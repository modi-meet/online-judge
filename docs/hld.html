01Problem Statement

A coding challenge is a competitive event in which participants solve algorithmic problems within a fixed timeframe. Solutions are submitted as source code, evaluated automatically against concealed test cases, and scored on the results.

An Online Judge is the platform that hosts these challenges. It must accept untrusted source code from thousands of strangers, execute it safely, evaluate it deterministically, and return a trustworthy verdict — while staying up during the exact minute everyone submits at once.

Two things make this hard, and they are the whole project:

  1. You are running arbitrary code from the internet on your own machines. Every submission is a potential fork bomb, an rm -rf /, a crypto miner, or an attempt to read the test case files sitting next to it.
  2. Load is not uniform. An online judge is idle for twenty-three hours and then takes its entire day's traffic in the final ninety seconds of a contest.

02Overview

Online Judge = Online Compiler + Processing Logic

InputOutputSemantics
Online Compilercode + optional custom stdinraw stdout / stderr / exit codeSynchronous. No judgement.
POST /run
Online Judgecode + problem_ida verdictAsynchronous. Same executor, N hidden test cases, plus comparison.
POST /submit

The judge is the compiler, plus a comparison loop, plus a scoring model. Build the compiler correctly and the judge is a thin layer on top; build it badly and no amount of judge logic saves you.

What makes this build different. Most online judge clones stop at “submit → verdict”. This one adds an AI Mentor whose answers are grounded in real execution, not an LLM's guess — the Dry-Run Simulator traces your code for real, and the Complexity Auditor measures your runtime at N = 10², 10³, 10⁴, 10⁵ and fits the curve. The execution plane built for judging becomes the mentor's evidence source. See §8.6.

03Scope

In scope by end of Level 4: auth, problem catalogue, code editor, online compiler, sandboxed judging, contests, live leaderboard, profiles, problem ingestion, AI Mentor (six modes), deployment, load testing, observability.

Explicitly out of scope: plagiarism detection (MOSS), payments, mobile apps, collaborative editing, video editorials, and writing our own compiler — we shell out to g++, javac and python3.

07Capacity Model

Sizing is done for one realistic contest, not a hand-wave.

Design target        : 10,000 registered users, 2,000 concurrent in a 2-hour contest
Submissions          : 2,000 users x 8 submissions          = 16,000 submissions
Average rate         : 16,000 / 7,200 s                     ~ 2.2 submissions/s
Peak (last 10 min)   : ~25% of volume in ~10% of the window ~ 5.5/s sustained, ~20/s spike

Cost of one judgement
  compile (C++, cached on repeat)                           ~ 0.6 s
  20 test cases x ~0.15 s typical                           ~ 3.0 s
  container start / teardown                                ~ 0.4 s
  ----------------------------------------------------------------------
  p50 ~ 4 s     worst case (all 20 cases hit a 1 s limit)  ~ 25 s

Concurrency needed — Little's Law, L = lambda x W
  steady : 5.5/s x 4 s   ~  22 judge slots
  spike  : 20/s  x 4 s   ~  80 judge slots

Slot footprint: 1 vCPU + 256 MB. A 16-vCPU node hosts ~14 slots.
  => 2 worker nodes steady, 6-8 at peak. Autoscale on queue depth, not CPU.

The queue is what makes this work. We do not size the fleet for the spike. We size for the steady rate, absorb the spike in the queue, and hold the p95 by draining. That is the entire answer to the thundering-herd problem.

Validating these assumptions

Every number above is a planning hypothesis derived from guesses about user behaviour. None of it is treated as settled. The computed fleet size sets the initial autoscaling bounds — it is not a fixed capacity, and it is not a commitment.

The V4 load test (§14) exists to replace this table's left column with measurements. Its deliverable is a revised §7, not a pass/fail. Until that revision exists, treat the worker count here as an order-of-magnitude estimate that happens to have arithmetic behind it.

08High Level Design

8.1Architecture

The system splits into three planes with different trust levels, different scaling curves, and different failure blast radii.

8.2Why three planes

PlaneTrustScales withFailure impact
ControlTrustedUsers onlineSite down — but no data loss
ExecutionZero trust — hostile code runs hereSubmissions/secVerdicts delayed, queue keeps filling. Site stays up.
IntelligenceTrusted code, untrusted outputAI requests + token budgetMentor unavailable. Judging unaffected.

Keeping these separate is the single most important structural decision. The API server must never compile or execute code. If it does, one fork bomb takes down the website.

The second structural rule is that dependencies point inward, never outward. The control plane depends on nothing in the intelligence plane; the execution plane depends on neither. Concretely: the judging path can run with the entire intelligence plane deleted, and that is verified by a chaos drill rather than assumed (§8.6).

8.3Flow: POST /run — the Online Compiler

Synchronous, no verdict, custom stdin, tighter limits.

  1. API validates { language, code, stdin? } and enforces a per-user token bucket in Redis.
  2. Job pushed to the high-priority queue — interactive traffic must never queue behind a contest backlog.
  3. Worker writes <uuid>.<ext> to a scratch dir, compiles, runs sandboxed with a 5 s wall cap and 256 MB.
  4. Returns { stdout, stderr, exitCode, timeMs, memoryKb }, output truncated at 64 KB.
  5. Scratch dir deleted in a finally block — always, including on timeout.

8.4Flow: POST /submit — the Judge

The verdict write is a compare-and-set on status (QUEUED|COMPILING|RUNNING → final), so a redelivered job can never overwrite a verdict that already landed. That is how we get idempotency without distributed transactions.

8.5Leaderboard

Read-heavy (everyone refreshes) and write-light (only on judged submissions) — so it is a materialized projection, never a live query against the submissions collection.

  • The projector consumes submission.judged and maintains a Redis sorted set per contest.
  • ICPC-style score packed into one double so a single ZREVRANGE is the whole read: score = solved × 10⁹ − penaltySeconds. Safe — doubles hold 2⁵³ ≈ 9×10¹⁵ exactly.
  • Clients get the top 50 over WebSocket. Deltas are pushed, not polled.
  • Degradation: if Redis is cold or lost, the projector replays the Kafka topic from the contest-start offset and rebuilds. Nothing is lost, because the event log — not Redis — is the source of truth.

8.6AI Mentor — the X-factor

Six modes, each mapped to a specific place a learner gets stuck. The design principle: an answer the system can verify beats an answer the model asserts.

01

Intuition Engine

“I have no clue.”

Breaks down the statement, classifies the pattern (sliding window, two pointers, grid search), names the edge cases — without dumping code.

02

Brainstorming Partner

“I have a clue and started.”

A sounding board for partial logic. Finds structural gaps, validates edge-case reasoning, nudges toward code without writing it.

03

Dry-Run SimulatorReal execution

“Written an approach, not sure it's correct.”

Not a model pretending to be a CPU. The code is instrumented and run in the sandbox on a small input; the actual variable trace is fed to the model, which narrates it and points at the exact line where state diverges.

04

Complexity AuditorReal measurement

“Solved, but TLE.”

Generates inputs at N = 10², 10³, 10⁴, 10⁵, measures runtime, fits the curve to an empirical complexity, then explains the hotspot and the optimisation that removes it.

05

Conceptual Translator

“I don't understand this data structure.”

Drops code entirely. Metaphors, diagrams and invariants — why a segment tree query is O(log N), how a trie routes nodes.

06

Foundations Architect

“New to this data structure.”

Primitives first — operations, insertion and deletion, memory layout — then the three canonical problems, pulled from our own catalogue by tag.

Modes 3 and 4 are the differentiator, and they are only possible because we already built a safe execution plane. Reuse it.

Three guardrails, non-negotiable:

  1. Leak guard. The mentor must never emit a working solution. Enforced in layers: mode-scoped system prompts; an output filter that rejects a response containing a complete compilable solution (full signature + control flow + return, above a length threshold); and per-problem editorial-similarity checks.
  2. Contest mode. The mentor is disabled during a rated contest, or its usage is recorded on the submission. Decided per contest, never left implicit.
  3. Context is assembled server-side. The client sends { problemId, mode, editorBuffer }. It does not get to declare what it is allowed to see — the service pulls the statement, the user's own recent verdicts, and sample-only test data.

Cost control: responses cached on (problemId, mode, sha256(code)); a per-user daily token budget in Redis; a cheap model for modes 1, 5 and 6 and a stronger one for 3 and 4; SSE streaming so time-to-first-token stays low.

8.7Problem Ingestion

An offline pipeline, never on the hot path. A pluggable SourceAdapter per site → normalizer → problems collection, retaining source, sourceUrl and attribution.

Flagging this honestly

Scraping statements from LeetCode or Codeforces raises copyright and terms-of-service issues. Default behaviour is metadata plus link only (title, tags, difficulty, URL) for third-party sources; full statements are stored only for our own or permissively-licensed problems. Codeforces has an official API — prefer it. This keeps the pipeline useful and the project publishable.

Scraped problems arrive without test cases. So the setter path is generator.py + brute.cpp — generate M inputs, run the brute-force reference to produce expected outputs, store the set with a version hash. This is how test data is actually authored in competitive programming, and it makes the platform self-sufficient.

8.8The mentor is optional by construction

The judge is the product; the mentor is an enhancement. If the intelligence plane is what takes the platform down during a contest, the differentiator has become the liability. So the independence is structural rather than a matter of care:

  • No inbound dependency. api and judge-worker never import the mentor. A lint rule and a CI dependency-graph check fail the build if that changes.
  • No synchronous call from the hot path. The mentor is reachable only at POST /api/ai/*. Nothing internal calls it, so an LLM provider timeout can never occupy an API worker or delay a submission.
  • Read-only data access. The mentor holds a database credential with no write grant. It cannot corrupt a submission, a verdict or a standing even through a bug.
  • Separate deployment and a kill switch. Its own process, health check and autoscaler; AI_ENABLED=false disables it instantly without touching anything else.

Verified, not asserted. A V4 chaos drill scales the mentor to zero replicas mid-contest. Pass condition: every submission still judged, standings still updating, and the only visible change is the mentor panel reporting itself unavailable. Contract detail in LLD §11.7.

10.4Verdict lifecycle

Every terminal status is written exactly once, by a compare-and-set against the pending states. A worker whose write matches zero documents knows another worker already finished and exits quietly — that is how a redelivered job is made harmless without distributed transactions. The write and its Kafka event share one transaction; see LLD §7.6.

11Security Posture

This platform's core function is to execute code written by anonymous strangers. Security is therefore not a section appended to the design — it is the constraint the architecture was shaped around. This section states what is defended, by what, and what an attacker gets when a layer fails.

11.1The trust boundary

There is exactly one: the edge of the execution plane (Fig 1, dashed band). Untrusted code runs inside it and nowhere else. The API service, the projector and the mentor never compile or execute a submission, so no amount of hostile input to them results in code execution.

11.2What the sandbox guarantees

Stated as properties rather than flags. The exact container configuration is LLD §6.4.

PropertyMechanism
No network access of any kindThe container joins no network — not a restricted one, none
Bounded memoryHard limit with swap disabled, so exceeding it is MLE and not a host OOM
Bounded, measurable CPUOne pinned core; CPU time accounted from the cgroup, not the wall clock
No fork bombsProcess-count limit inside the container
No privilege escalationAll capabilities dropped, no-new-privileges, non-root uid, seccomp allowlist
Immutable filesystemRead-only rootfs; the single writable mount is noexec
No disk exhaustionFile-size ulimit plus a 64 KB output cap → OLE
No access to answersTest cases arrive on stdin; nothing is ever mounted into the container

11.3Infrastructure containment — assuming the sandbox fails

A container boundary is one kernel bug away from not being a boundary. The design assumption here is that it will eventually fail — a kernel CVE, a runtime regression, a flag we got wrong. So the question this section answers is not “can they escape” but “what do they get if they do”.

The answer is: a bare, credential-less node with no route to anything that matters.

ControlWhat it denies an attacker who is already root on the node
Dedicated, tainted node poolNo control-plane component, no API pod, no projector and no other service shares that kernel. Judge nodes run judge workers and nothing else.
No cloud credentials on the nodeInstance metadata is blocked at the network layer (IMDSv2, hop limit 1, plus a firewall rule on 169.254.169.254). The node's instance profile grants nothing. The worker's S3 access is a short-lived scoped token held in process memory, never written to disk.
No cluster secretsautomountServiceAccountToken: false, no image-pull secrets, no kubeconfig, no database password anywhere on the host.
Egress denied by defaultThe judge subnet has no NAT gateway and no internet route. Outbound is allowed only to the S3 VPC endpoint, Redis and Kafka, on specific ports. An escaped process cannot phone home, exfiltrate, or pull a second stage.
Ingress deniedNo inbound rules except the health check from the load balancer subnet.
Nothing durable on the nodeEphemeral root volume, tmpfs scratch, and a 24-hour maximum node lifetime. An implant does not survive the day.
Least-privilege data reachA VPC endpoint policy scopes S3 to the code and test case prefixes, read-only for test cases. Reaching S3 does not mean reaching the bucket.
Kernel hygieneAuto-patched node images, a forced monthly AMI roll, and user-namespace remapping so container root maps to an unprivileged host uid.
Upgrade pathIf we ever host public untrusted contests, the runtime moves to gVisor or Firecracker microVMs — a per-submission kernel boundary rather than a shared one. Costed in §16, not adopted speculatively.

Blast radius. The worst realistic outcome is one compromised, credential-less, network-isolated node that is destroyed within twenty-four hours. It holds no user data beyond the test cases for problems being judged at that moment, and it cannot reach the control plane, the database, the object store beyond two prefixes, or the internet.

11.4Detection and response

Containment without detection means an attacker gets twenty-four hours undisturbed. Judge nodes run a syscall monitor (Falco, or auditd rules) alerting on:

  • execve of anything outside the runner's allowlisted binaries
  • writes outside the tmpfs scratch mount
  • any outbound connection attempt — there should never be one
  • setuid, kernel module loads, or writes to /proc/sys

An alert cordons the node automatically, snapshots it for forensics, and replaces it. Every alert carries the submissionId occupying that slot at the time, so the responsible source code is one query away — and it is retained for 14 days alongside the per-test-case execution record.

11.5Invariant: host execution never leaves a laptop

V0 executes code directly on the host with child_process and no isolation, so that the editor and the /run path can be built before the sandbox exists. This is a development affordance and a serious vulnerability if it ever ships.

Invariant. The host executor is unreachable outside local development, enforced independently at four levels — a boot guard that throws on NODE_ENV=production, a CI check that fails the build if the production bundle imports it, an env schema that rejects the enabling flag in production, and the fact that V0 is never deployed at all: staging begins at V1, after the sandbox lands. The package is deleted outright when V1 merges. Implementation in LLD §6.6.

12Key Decisions & Tradeoffs

DecisionChosenAlternativeWhy
Dispatch vs event log Redis/BullMQ for the work queue, Kafka for the event log Kafka for both Kafka is a log, not a work queue — no per-message ack, no visibility timeout, no priorities, and long-running consumers trigger rebalance storms. A work queue gives us leases, retries and a priority lane for /run; Kafka gives us replayable fan-out for the leaderboard, analytics and audit. Using each for what it is good at is the honest answer, and a better interview answer than “we added Kafka”.

Adoption trigger — Kafka is not built until it is earned. V1 ships BullMQ alone, with the worker updating the standings projection directly. Kafka enters in V2 only if a second independent consumer of judged events actually exists — analytics, notifications, or an audit trail somebody queries. If the projector is still the only consumer when V2 opens, Kafka is deferred and revisited at V3. Two message systems is a real operational cost, and it has to be paid for by a real second consumer rather than by an architecture diagram.
IsolationDocker + seccompgVisor, Firecracker, isolate Docker with dropped capabilities is enough for a self-hosted, non-nation-state threat model and is by far the fastest to ship. Upgrade path to gVisor documented for the day we host untrusted public contests.
Primary datastoreMongoDBPostgreSQL Chosen for MERN continuity and flexible statements. Noted risk: contest scoring is inherently relational and transactional. If scoring correctness bites, submissions and contests move to Postgres while problems stay in Mongo.
Container strategyCold docker run per submission in V1, warm pool in V3Warm pool from day one A ~400 ms cold start is affordable at our rate and is the strictly safer default — a fresh filesystem every time. Optimise when measurements demand it, not before.
Verdict deliverySSE per submission, WebSocket for standingsPolling everywhere Polling at contest scale is exactly the read storm the projection was built to avoid.
AI groundingExecution-backed for modes 3 and 4Pure LLM for all six A traced run and a measured runtime curve are facts. This is the project's differentiator and it costs little, because the execution plane already exists.
AI couplingNone — separate service, separate failure domainMentor embedded in the API service Embedding is simpler right up until the first provider outage, at which point hung LLM calls occupy API workers and submissions queue behind them. The differentiator must not be able to take down the product. Enforced by lint and a dependency-graph check, verified by a chaos drill — §8.8.

14Testing Strategy

LayerWhat
UnitComparators (trailing newline, CRLF, float tolerance), score packing, state machine transitions
IntegrationReal Docker. A fork bomb must yield RE, an infinite loop TLE, a 1 GB allocation MLE, and a network call must fail.

15Observability

Metrics. submission_queue_depth (the autoscaling signal), judge_duration_seconds (histogram by language), verdict_total{verdict}, sandbox_oom_total, sandbox_timeout_total, worker_slots_busy, ai_tokens_total{mode}, leak_guard_triggered_total.

Traces. One OpenTelemetry trace per submission spanning API → enqueue → worker → Kafka → projector. submissionId is the correlation ID everywhere, logs included.

Alerts. Queue depth above 500 for five minutes · p95 verdict above 60 s · DLQ non-empty · IE rate above 1% · fewer than two healthy workers.
